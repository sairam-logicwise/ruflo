## Critical

### C1. A hand-written `status: done` passes every check — requirement 8 is defeated

Two reviewers proved this independently, with executed probes. I confirmed the root cause by reading:

```
statesToAudit('done') -> ['drafted', 'specified', 'implementing']
```

`phase-check.ts:39-46` audits the states *before* `done` but never `verifying` — the one transition that carries the test gate. A record with `status: done`, `doneCriteria.testLayers: ['unit','e2e']`, `coverageThreshold: 95` and no test ever run produces:

```
record validate    -> [OK] All record(s) valid.
record phase-check -> [OK] All task record(s) are phase-gate consistent.  EXIT=0
```

`contentHash` covers the body only (`content-hash.ts:20`), so editing frontmatter trips nothing. Any agent with file-write access — which is every tool's built-in editor — writes `done` and the system agrees.

**Deeper cause:** `applyTaskTransition` (`records-io.ts:137-150`) writes `status` and discards the `TestRunResult`. There is nowhere on the record that says tests ran, so nothing downstream can check. The design principle was "quality is derived from evidence" — the evidence is thrown away.

**Fix:** persist a verification receipt (command, exit code, coverage, timestamp, git SHA) on the transition, and make `phase-check` fail any `done` task with non-empty `testLayers` whose receipt is missing or predates the current content hash.

**Closed 2026-09-23.** Implemented exactly as prescribed: `VerificationReceiptSchema` (docops) persists command/exitCode/coverage/timestamp/gitSha/contentHash; `task-verify.ts`/`task-repair.ts`/`run.ts` all write it on a real test run; `phase-check.ts`'s new `auditDoneReceipt()` fails a `done` task with non-empty `testLayers` whose receipt is missing or whose `contentHash` no longer matches the record's current one. Reproduced the exact exploit against a real hand-crafted repo via the compiled CLI: `record validate` still passes (correct — schema shape is fine), `record phase-check` now fails it: `"status is done with required test layers (unit, e2e) but carries no verification receipt at all"`. **Residual, not closed by this fix:** the receipt is still not cryptographically unforgeable — `computeContentHash` is unsigned, so a determined forger who hand-computes it could still write a fabricated receipt with a matching hash. Important 5 (closed 2026-09-23, below) extended the hash to cover the whole frontmatter, closing the "edit one field, hash still matches" exploit this note originally flagged, but not the class of forgery neither fix ever claimed to close — that would need a signing key, out of scope for either item.

### C2. There is no MCP surface — requirement 1 is unimplemented

`mcp-client.ts:197` registers `quoteTools` and nothing else. There is no `record`, `run`, `phase-check`, `decompose` or `backfill` MCP tool — confirmed by listing `mcp-tools/`, which contains exactly one relevant file.

The entire workflow is CLI-only. The gate lives inside CLI command bodies, so it is reachable only by a tool that chooses to shell out to `ruflo run`. A Cursor or Codex agent has nothing to be gated by; it simply doesn't call the command.

This is the load-bearing claim of the whole architecture — "the record is the gate, not the prompt", enforced in the MCP client path so it survives a tool switch. That path was never built. `authorizeMcpTool` is untouched.

**Closed 2026-09-23.** New `command-bridge.ts` adapts a real `Command`'s own `action` into an MCP tool handler (one implementation, two entry points, generalizing T11's own `quote-tools.ts` pattern); `record-workflow-tools.ts` registers 20 tools covering every leaf command under `record req/decision/task`, `record validate`/`phase-check`/`decompose`, `run`, and `backfill summarize/infer`. Verified end to end via `ruflo mcp exec` alone, no CLI shell-out: created a requirement, cited it from a task, ran `run` (blocked on the real unaccepted-citation gate), confirmed the requirement via `record_req_confirm`, ran `run` again — the same task moved past that exact block. `authorizeMcpTool` itself remains untouched, as noted — this fix makes the commands reachable and gated via MCP; it does not add a NEW policy layer on top.

### C3. The calibration corpus measures the wrong kind of work — requirement 2's foundation

D5 approved $50 for 15-20 tasks at $2-3 each. The 16 records total **$0.20** — 0.4% of budget.

| Metric | Expected (D5) | Actual |
|---|---|---|
| Total spend | ~$40 | **$0.20** |
| Per task | $2-3 | **$0.0126** |
| Mean output tokens | — | **216** |

216 output tokens is a paragraph. These records capture a model *answering a question about* a task, not an agent *completing* one — no multi-turn work, no file reads, no retries. Real agentic tasks cost dollars precisely because of those things.

So the estimator is not merely calibrated on approximated numbers. It is calibrated on a **different kind of work**, roughly two orders of magnitude smaller than what it will be asked to quote. Every quote inherits that.

`HANDOVER.md` §9 is honest that the numbers are approximations. It does not say they are approximations *of the wrong activity*.

**Closed 2026-09-23 — the cheapest honest path this review itself named, taken, not the pilot re-run.** Added a required `source: 'proxy' | 'measured'` + `priceModel` to `ActualsSchema` (Important 11, folded in here since it's the same fix) — never optional, and backfilled all 16 real T8 records as `proxy`. `EstimatorRow` now carries a real `measured: boolean` propagated from that field (trajectory rows are always `true` — real router production outcomes). `quote.ts` now refuses to state a dollar figure — `lowCostUsd`/`highCostUsd` are `undefined`, with an explicit `costCaveat`, not a silently-computed number — unless the corpus behind it has at least one really-measured row; the token range is unaffected. Verified for real against this repo's own records: `ruflo quote REQ-001` now prints `"no measured cost data yet"` instead of a dollar figure. The corpus itself is still T8's proxy pilot data — not re-run against real multi-turn agent work, exactly the tradeoff this review itself recommended over re-running it.

### C4. `quote` over-prices by 3.17x

`quote.ts:213` prices as `tokens * blendedPrice(id) / 4_000_000`. `blendedPrice` is `in + 3*out` (`model-prices.ts:105`) — a hardcoded 25% input / 75% output mix, giving an effective $12/Mtok at sonnet rates.

The corpus it reads is **93.5% input / 6.5% output** (49,725 in / 3,458 out), which prices at $3.78/Mtok.

```
as-priced effective rate : $12.00/Mtok
rate at real corpus split: $3.78/Mtok
over-pricing factor      : 3.17x
```

This is independent of C3 and fixable now with no new data: `EstimatorRow` already carries `inputTokens` and `outputTokens` separately before collapsing them (`predict.ts:128`). Carry the ratio through and price with `costUsd()`.

No test pins any dollar figure — `quote.test.ts:105` only asserts `> 0`.

**Closed 2026-09-23.** `predict.ts`'s `Estimate` now carries the REAL input/output split from whichever neighbour row actually set each edge of the range (`lowInputTokens`/`lowOutputTokens`/`highInputTokens`/`highOutputTokens` — the exact real neighbour's own ratio, not a blended average across all neighbours); `quote.ts` prices with `costUsd()` against that real split instead of `blendedPrice()`'s fixed mix. New test pins an exact dollar figure (`(900*3 + 100*15) / 1_000_000` for a 9:1 real input:output row at sonnet rates) and asserts it is below what the old formula would have produced, so a future regression back to the blended-guess formula would be caught by an exact number, not just a `> 0`.

### C5. `ruflo variance` reports a 100% hit rate it knows is meaningless

`variance.ts:18-33` states plainly that the figure is tautological: the 16 records' `estimate` is a synthetic ±20% band computed from their own `actuals`, before the estimator existed. The real hold-out figure is 75%.

The module doc says this is "reported plainly… see the CLI's own `--json` output". It is not. `VarianceReport` (`variance.ts:68-75`) has no caveat field, and `commands/variance.ts:19` prints the bare `100.0% hit rate` as its first line.

A stakeholder running `ruflo variance` today concludes the estimator is perfect. This is the single most misleading user-facing output in the system, and the code that produces it contains a correct explanation of why it is wrong.

**Closed 2026-09-23.** Using the same `measured`/`proxy` distinction C3's fix introduced: `VarianceReport` now carries `measuredHitRate`/`measuredSampleSize` (computed ONLY from really-metered rows — an honest `0` on this repo's own records today, not a hidden one) and a `hitRateCaveat` that fires whenever any proxy row is mixed into the headline `hitRate`. `commands/variance.ts` prints the caveat BEFORE the bare hit-rate line, not after and not only in a doc comment. Verified for real: `ruflo variance` against this repo's own 16 records now prints `"⚠ all 16 task(s) behind this hit rate are proxy-only (T8's calibration pilot) — this compares each task's synthetic estimate band to itself, not real estimator accuracy; see estimator-holdout-check.mjs's real 75.0% hold-out figure instead"` as its first line, followed by the same `100.0%` figure — now correctly framed, not hidden.

## Important

**Enforcement**
1. **The citation gate is self-serviceable.** `record req new --title X --status=accepted` then cite it — verified end to end. T16 checks *that* a record is accepted, never *who* accepted it. `--provenance` defaults to `human` with no verification. **Closed 2026-09-23** — `--status` removed entirely from `req new`/`decision new` (same fix already applied to `task new` after the analogous `--status=done` bypass); every new record starts `draft`, `accepted` only reachable through `req confirm`/`decision confirm` (T24). `--provenance` verification (item unaddressed — still no check on WHO sets `provenance: human`) is a separate, smaller residual gap.
2. **No branch protection on `main`** — confirmed 404. T17's CI job blocks no merge. Its third check is `continue-on-error: true` and passes if *any* changed path starts with `docs/tasks/`, which a one-character edit satisfies.
3. **`isLegalTransition` has zero production callers** (`state-machine.ts:189`). The 36-pair matrix test proves a function nothing calls; no written record is ever validated against its previous status.
4. **`run.ts:206` trusts `blocked.fromState` read off disk** — forged frontmatter gets a free advance to `verifying`.
5. **`contentHash` covers the body, not the frontmatter** — every gate-relevant field sits outside the integrity check. This is why C1 works. **Closed 2026-09-23.** `computeContentHash` (docops) now hashes the whole canonicalized frontmatter (every nesting level, key-order independent) plus the body, excluding only `contentHash` itself. Every writer across the codebase (3 `record new` commands, `backfill.ts`, `decompose.ts`, `record validate --fix`, and a new `finalizeContentHash()` helper for post-creation mutators) follows a "build fields, hash, merge" order so none of them can write a self-inconsistent record. Two real bugs surfaced closing this, both fixed in the same change:
   - **The fix itself broke C1's own receipt check.** `buildVerificationReceipt` stamped a receipt with the record's PRE-transition `contentHash`; once the hash covers frontmatter, ANY transition (e.g. `verifying -> done`) changes the POST-transition hash, so a genuinely fresh receipt would read as stale on every real write — C1 would have silently stopped working the moment this landed. Fixed by excluding `verification` from what `computeContentHash` hashes too (same treatment as `contentHash` itself, for the same circularity reason) — the receipt's hash and the record's top-level hash become the same formula over the same fields regardless of transition order. Documented in `content-hash.ts` and locked in with dedicated docops tests.
   - **`auditDoneReceipt` (phase-check.ts) never checked `verification.exitCode`.** A hand-written `done` with a fabricated receipt claiming `exitCode: 0` — or, found while auditing this, one claiming any exit code at all, since only presence and hash-matching were checked — passed silently. Added a direct `exitCode !== 0` check.
   - Also found and fixed the identical missing-rehash bug in `task-ready.ts` (`implementing -> verifying`) and `confirmRecord` (`req`/`decision confirm`) — both called `applyTaskTransition`/mutated frontmatter without ever recomputing the hash, a latent bug the old body-only scheme never exposed because neither touches the body.
   - Verified end to end against a real hand-crafted repo via the compiled CLI: a hand-edited frontmatter field is caught by `record validate` and fixed by `--fix`; a full `req new -> confirm -> task new -> run -> task ready -> task verify` cycle with a real `npm test` subprocess produces a `done` record whose `verification.contentHash` equals its own top-level `contentHash`, and both `record validate` and `record phase-check` pass; hand-editing the receipt's `exitCode` to `1` is now caught by `phase-check`. All 37 real records in this repo migrated via `record validate --fix` in this same commit (none carried a `verification` block, so the migration was a pure rehash, nothing to clear).

**Autonomy and QA**
6. **The loop cannot complete a task.** Nothing advances `implementing → verifying`: `run.ts:262` skips it by design, `task-verify.ts:65` refuses anything not already `verifying`. The only way forward is hand-editing a record — the exact hole T18/T19 exist to close. Requirement 7 is unmet end to end. **Closed 2026-09-23** — new `ruflo record task ready <id>` command advances `implementing -> verifying` (still never auto-advanced by `ruflo run`, by design — this is the one deliberate human/agent judgement call the state machine has, not an evidence gate). Verified end to end via the compiled CLI: a task stuck on "implementing" advances to "verifying" for real once `record task ready` runs.
7. **`testLayers` is decorative.** `test-runner.ts:114` consults only `length === 0`; one `npm test` satisfies `['e2e','automation']` identically. `automation` isn't even in the `TestLayer` union. **Correction, 2026-09-24, two peer sessions cross-checking a calibration tranche (T8 follow-up):** the `automation` claim needed a citation and had two different, both-real answers depending on which `TestLayer` type it means. `docops/src/schemas/task.ts:106` — the schema a hand-written or agent-written `doneCriteria.testLayers` validates against — does include `'automation'`. `cli/src/ruvector/estimator/features.ts:32` — a separate, locally-defined `TestLayer = 'unit' | 'integration' | 'e2e'` used by the inference function `findTestLayers()` — does not. Both were verified directly by reading each file. The real, sharper finding neither session stated correctly the first time: a human or agent can hand-write `testLayers: ['automation']` on a task (schema allows it), but `findTestLayers()`'s own inference can never propose `'automation'` on its own — it has no keyword branch for it, matching its narrower type. The two `TestLayer` definitions have drifted apart. That's worth its own small fix (either widen `features.ts`'s union to match the schema, or explain in a comment why inference deliberately excludes it) independent of the decorative-check gap above.

9. **The spend ceiling is per-invocation and checked before-only.** A supervisor re-invoking after a crash gets N × the ceiling, and a repair can overshoot by a full `--repair-budget`.

11. **`actuals` has no provenance field.** Once T13 writes real metered actuals, proxy and measured rows are byte-identical in the corpus and can never be separated or reweighted. Add `source` and `priceModel` now, and backfill the 16. **Closed 2026-09-23** — done exactly as prescribed, as part of C3's fix: required `source`/`priceModel` added to `ActualsSchema`, all 16 backfilled as `proxy`, T13's `buildRepairActuals()` now stamps real repair spend as `measured`.

13. **Confidence is blind to provenance** (`predict.ts:92`). It measures corpus *density*, not corpus *validity*, and would return the same score for real data. **Sharpened, 2026-09-24, same T8 calibration cross-check:** confirmed directly — `computeConfidence` (`predict.ts:118`) has zero references to `measured` anywhere in its body, while `EstimatorRow` already carries a real `measured: boolean` field (`predict.ts:40`, set from `task.actuals.source === 'measured'` in `corpus.ts:274`). The signal this item asks for already flows through the pipeline on every row; `computeConfidence` simply never reads it. That makes the real fix smaller than "confidence is blind to provenance" implies — no new data plumbing needed, just folding an existing field into the existing formula (e.g. a `provenanceTrust` factor derived from `neighbors.filter(n => n.row.measured).length / neighbors.length`).

**Plain English**

Enforce it in the schema. **Partially closed 2026-09-23** — the concrete exploit is gone (Important 1's fix removed `--status` from creation entirely, so this specific combination can no longer be produced via the CLI).
